# Asanchez

MVP: агент, который следит за единым стандартом ведения задач во всех
проектах Gestión Operativa (Prestige Expo). Реагирует на новые задачи и на
правки конкретно тех полей, которые сам проверяет (название, описание,
исполнитель, срок) — чтобы довести до конца недоделанное (например,
добавили описание на испанском, но забыли перевод). Любые другие правки
(комментарии, кастомные поля и т.п.) игнорируются — старые задачи агент не
«перетряхивает».

Для каждой такой задачи:

- проверяет, что название на испанском и из него понятно, что нужно сделать
  — главное ясность, а не строгая грамматика: название вида "Factura
  electricidad Casa A" уже валидно само по себе, даже если не начинается с
  глагола (`[Verbo infinitivo] + complemento` — это ориентир только для
  переформулировки неясных названий, а не обязательный формат для всех).
  Если задача названа не на испанском, или по-испански, но реально
  непонятно, что делать, а суть всё же угадывается — **сам переводит и/или
  переформулирует**, сохраняя смысл, с прозрачным комментарием об этом.
  Если само действие понять нельзя (слишком расплывчато/двусмысленно,
  независимо от языка) — не угадывает, а спрашивает автора;
- следит, что описание (Notes) заполнено на испанском и русском (`[ES]\n---\n[RU]`):
  добавляет шаблон или недостающий перевод, не переписывая уже написанный текст;
- ищет возможные дубли среди существующих задач проекта и еженедельно
  (по воскресеньям) сводным отчётом по всем проектам — только помечает их
  комментарием, **не закрывает и не удаляет** задачи;
- проверяет, что указаны исполнитель и срок — если чего-то нет, пишет
  автору задачи в комментарии с просьбой указать; **не назначает исполнителя
  и не ставит срок сам**;
- всё перечисленное выше публикуется **одним** сводным комментарием (не
  несколькими), с настоящим `@-упоминанием` автора задачи — он получает
  уведомление от Asana.

Комментарии агента — только на испанском (единый язык коммуникации с
командой). Notes (описание задачи) остаются двуязычными ES+RU: заполнить
нужно только испанскую часть, перевод на русский — всегда задача агента, он
добавляет его молча, без отдельного комментария.

**Ответы на упоминания.** Если кто-то упомянет `@Asanchez` в комментарии
задачи, агент реагирует одним комментарием (на испанском, с упоминанием
спросившего), опираясь на контекст задачи и предыдущие комментарии:

- просто вопрос, или просьба неоднозначна — отвечает текстом (не
  предпринимает действий);
- прямая и однозначная просьба поправить задачу (например «поправь сам») —
  **сам** исправляет название и/или описание;
- прямая и однозначная просьба разделить/декомпозировать задачу на две —
  **сам** сужает текущую задачу до первой части и создаёт новую задачу на
  вторую;
- если при этом явно назван исполнитель и/или срок (например «назначь на
  Лауру, срок через неделю») — **сам** назначает: имя резолвится ТОЛЬКО среди
  участников самого проекта (не всего воркспейса — тёзок/похожих имён там
  может быть много), с учётом уменьшительных имён и вариантов написания
  ("Наташа" = "Nataliia" и т.п.); назначается только при ровно одном
  совпадении среди участников проекта (иначе — просьба назначить вручную,
  без угадывания); срок считается от текущей даты.

Действует только при полной уверенности в деталях (в т.ч. по своим же
прошлым комментариям в этой задаче) — иначе просто переспрашивает, не
угадывая. Закрытие/удаление задач — вне этой возможности, даже если
попросят в упоминании: это делает человек. Автоматическое поведение на
новых задачах (напоминание про исполнителя/срок) не меняется — это
по-прежнему просто напоминание, без явной инструкции от человека тут
угадывать некого.

Технически это отдельный проход: Asana Events API не отдаёт события о новых
комментариях для проекта, поэтому агент при каждом опросе дополнительно
проверяет задачи, изменённые с последней проверки (`state/mention-checkpoints.json`),
и смотрит их комментарии на упоминания.

## Как это работает: GitHub Actions по расписанию

Продовый вариант — **без постоянно работающего сервера**. Вместо вебхуков
Asana агент сам периодически опрашивает изменения через
[Events API](https://developers.asana.com/docs/get-events-on-a-resource) и
запускается GitHub Actions прямо в этом репозитории:

- **`.github/workflows/poll.yml`** — каждые 5 минут опрашивает включённые
  (`enabled: true`) проекты из `config/projectCodes.json`: обрабатывает новые
  задачи (`added`) и правки отслеживаемых полей — name/notes/assignee/due_on
  (`changed`); остальные события игнорируются. Коммитит обратно
  `state/sync-tokens.json` — курсор Asana Events API между запусками.
- **`.github/workflows/weekly-duplicate-scan.yml`** — раз в неделю (воскресенье,
  08:00 UTC) сканирует все включённые проекты на дубли и публикует сводный
  отчёт (раздел 4, триггер 2).

Реакция не мгновенная (до ~5 минут задержки вместо вебхука в реальном
времени), зато не нужен отдельный хостинг, домен и TLS — всё крутится в
самом GitHub, на бесплатных раннерах.

> Постоянный сервер с вебхуками (`src/index.ts`, `src/webhook/`) в коде
> остался как альтернатива — см. раздел «Альтернатива» ниже, если позже
> понадобится реакция в реальном времени и появится место для деплоя.

## Архитектура

- **Node.js / TypeScript**.
- **Asana REST API** (Personal Access Token) — чтение задач, Events API для
  поллинга, добавление комментариев, обновление Notes.
- **Claude (Anthropic API)** — используется для «смысловых» проверок,
  которые не решаются регулярками: действительно ли слово — испанский
  глагол в инфинитиве, перевод ES↔RU, и итоговое подтверждение дублей
  (чтобы не путать «Factura electricidad Casa A» и «Factura electricidad
  Casa B» — разные объекты с похожими словами).

```
src/
  asana/        — клиент Asana REST API (включая Events API)
  claude/       — клиент Anthropic API (переводы, инфинитив, оценка дублей)
  rules/        — правила из разделов 1, 3, 4 инструкции
  engine/       — дерево решений (раздел 5) и еженедельный скан дублей
  scripts/
    pollProjects.ts     — опрос Asana (запускает poll.yml)
    runWeeklyScan.ts    — недельный скан дублей (запускает weekly-duplicate-scan.yml)
    registerWebhooks.ts — для альтернативного сценария с постоянным сервером
  webhook/, index.ts     — постоянный сервер с вебхуками (альтернатива, см. ниже)
config/projectCodes.json — справочник кодов проектов (раздел 7)
state/sync-tokens.json   — курсоры Asana Events API между запусками poll.yml
```

## Настройка

### 1. Секреты GitHub Actions

Settings → Secrets and variables → Actions → New repository secret:

| Секрет | Назначение |
|---|---|
| `ASANA_ACCESS_TOKEN` | Personal Access Token — https://app.asana.com/0/my-apps |
| `ANTHROPIC_API_KEY` | Ключ Anthropic API (нужна пройденная верификация аккаунта на console.anthropic.com, иначе запросы будут падать с `Identity verification is required`) |
| `REPORT_PROJECT_GID` | (опционально) GID проекта, куда публикуется сводный отчёт о дублях — пока не задан, недельный скан просто логирует предупреждение и ничего не публикует |

Опционально — Settings → Secrets and variables → Actions → Variables:
`ANTHROPIC_MODEL` (по умолчанию `claude-sonnet-5`).

Workflow `poll.yml` коммитит `state/sync-tokens.json` обратно в репозиторий,
поэтому ему нужен `permissions: contents: write` — это уже прописано в файле
и работает через встроенный `GITHUB_TOKEN`, дополнительно ничего заводить не
нужно.

### 2. Справочник проектов

В `config/projectCodes.json` перенесена таблица из раздела 7 и сверена с
реальным workspace Asana. По факту проект `<КОД> - Gestión Operativa`
сейчас существует не для всех кодов — GID заполнен только там, где такой
проект реально есть (см. поле `_status` в файле). Для остальных кодов есть
только «N. Bandeja de entrada» (неразобранные задачи) — туда агента
подключать нельзя, эти задачи как раз и есть типичные ошибки из раздела 1.

Раскатывание на проекты управляется полем **`enabled`** у каждой записи —
это отдельный рубильник от `operational`/GID, чтобы можно было включать
проекты по одному:

```json
{ "code": "LDV", "asanaProjectGid": "1215192498626040", "operational": true, "enabled": true }
```

**Сейчас включено 9 проектов**: LDV, TTN, BSQ2, NHB, BSB, APR, CAM, OFP, VHN —
для всех подтверждён GID и участие агента («Asanchez») в проекте. Остальные
коды в реестре есть (для справки и GID), но `enabled: false`, потому что для
них в Asana пока не существует отдельного проекта `<КОД> - Gestión
Operativa` — агент их не трогает. Чтобы подключить следующий проект (как
только он появится в Asana и агент будет туда добавлен участником),
поменяйте его `enabled` на `true` (и заполните `asanaProjectGid`) — новый
`poll.yml` подхватит его на следующем запуске, ничего пересоздавать не нужно
(это не вебхук, а просто список опрашиваемых проектов).

Общий проект «Actas de reuniones» (протоколы встреч всех кодов) уже найден
(`actasProjectGid`), но тоже выключен (`actasEnabled: false`) до отдельного
решения.

**Ответственный проджект-менеджер по коду** — не в этом JSON, а в Asana:
портфолио **«Desarrollo Inmobiliario»** (gid `1215192498625883`) содержит по
одному stage-gate проекту на каждый код, и у каждого — кастомные поля `PM`,
`TC`, `Fin. Responsable` (people-поля). Это понадобится, когда Asanchez
будет согласовывать протоколы совещаний с ответственными (следующий этап,
после Actas de reuniones) — пока только для справки, в логику агента не
подключено.

### 3. Первый запуск

Ничего вручную запускать не нужно — как только секреты заданы и Actions
включены в репозитории (Settings → Actions → General → разрешить), workflow
`poll.yml` начнёт выполняться по расписанию. Можно запустить его сразу
вручную: вкладка Actions → «Asanchez — опрос Asana» → Run workflow.

На первом запуске для каждого проекта Asana Events API не отдаёт события
«задним числом» — агент просто запоминает стартовую точку синхронизации и
ничего не комментирует у уже существующих задач. Реагировать он начнёт на
изменения, которые произойдут **после** этого первого запуска.

### 4. Локальная разработка

```
npm install
cp .env.example .env   # заполнить ASANA_ACCESS_TOKEN и ANTHROPIC_API_KEY
npm run poll           # разовый опрос всех включённых проектов
npm run weekly-scan    # разовый скан дублей
npm run typecheck
```

## Альтернатива: постоянный сервер с вебхуками (реальное время)

Если в будущем понадобится реакция без задержки в несколько минут и появится
хостинг с публичным HTTPS-адресом (свой сервер, Railway, Fly.io, Docker-хост
и т.п.) — в репозитории уже есть готовый вариант на Express + вебхуках Asana.

```
npm run dev              # локально, для теста (нужен туннель типа ngrok, чтобы Asana достучалась)
npm run build && npm start
docker build -t asanchez . && docker run -p 3000:3000 --env-file .env asanchez
```

Дополнительно к секретам из раздела 1 нужны:

| Переменная | Назначение |
|---|---|
| `PORT` | Порт HTTP-сервера (по умолчанию 3000) |
| `PUBLIC_BASE_URL` | Публичный HTTPS-адрес сервиса — Asana шлёт туда вебхуки |
| `ASANA_WEBHOOK_SECRET` | Заполняется автоматически после первого handshake |

Регистрация вебхуков (сервис должен уже быть запущен и доступен по
`PUBLIC_BASE_URL`):

```
npm run register-webhooks
```

Скрипт создаёт вебхук на каждый включённый проект. Asana сразу присылает
handshake-запрос — сервис сам сохраняет секрет в `.webhook-secret` (в `.env`
можно тоже зафиксировать `ASANA_WEBHOOK_SECRET`, чтобы секрет пережил
пересоздание контейнера). Убедитесь, что `.webhook-secret` персистентен
(volume) либо `ASANA_WEBHOOK_SECRET` задан в окружении — иначе после
рестарта контейнера подписи вебхуков перестанут проверяться (401).

При этом сценарии `DUPLICATE_SCAN_CRON`/`DUPLICATE_SCAN_TZ` управляют
встроенным `node-cron` вместо `weekly-duplicate-scan.yml`.

## Что агент никогда не делает без разрешения человека

- переименовывает название только когда уверен в сути задачи; если нет —
  спрашивает, а не угадывает и не переименовывает вслепую;
- не закрывает задачи;
- не удаляет задачи (в т.ч. подозреваемые дубли);
- не назначает исполнителя и не ставит срок сам по себе — только просит
  автора задачи указать недостающее. Исключение: явная, однозначная просьба
  в упоминании ("назначь на Лауру") — тогда назначает, но и там не угадывает
  между несколькими тёзками/неизвестным именем;
- не трогает задачи из-за правок, не относящихся к name/notes/assignee/due_on
  (комментарии, кастомные поля и т.п. не перезапускают проверки).
